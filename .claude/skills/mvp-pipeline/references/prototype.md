# プロトタイプ生成（DS エンジン）

分析・設計の成果物から、**クリックして触れる単一 HTML** を作る。
Web アプリ本体の「DS エンジン」（`src/lib/prototype-ds/`）と同じ仕組み・同じ骨格を使う。

## 中心にある考え方: 骨格はコード、画面だけ LLM

```
骨格（コード固定）                    画面（LLM が書く）
──────────────────────            ──────────────────
CDN 読み込み・Babel 変換              function Screen() {
AppShell（2階層サイドバー）             return (
Page コンポーネント                       <Page title="顧客一覧">
navigate() ルーター                        ...
テーマ CSS 変数                          </Page>
                                       );
                                     }
```

LLM に HTML 全体を書かせない。**1画面 = 自己完結した React 関数コンポーネント1つ**だけを
書かせ、`buildDsHtml()`（`src/lib/prototype-ds/shell.ts`）が骨格に埋め込む。
これで構造崩れ・途中切れが全体を壊すことがなくなり、1画面が失敗しても
その画面だけプレースホルダに落ちて残りは無事に動く。

## 画面ユニットの導出

`artifacts/navigation.json` の `items` から、生成する画面を機械的に決める
（`deriveScreenUnits()`。Web アプリと同じ関数）。

1. **親はグループ見出し**。他項目の `parent` になっているラベルは画面を作らない。
   例: `AI運用設定` が `精度検証` の親なら、`AI運用設定` はメニューの見出しになるだけ。
2. **一覧には詳細を補う**。`screenType` に `list` を含む画面ごとに `「◯◯詳細」` を追加する。
   これはメニューには出さず、一覧側から `navigate("◯◯詳細")` で開く。

結果、ナビ 6 項目 → 生成対象 9 画面、のように増える。

## 画面間の遷移

`navigate("画面名")` はグローバル関数。**プロンプトの「# 遷移」に書かれた画面名にだけ**使う。
画面名を発明すると存在しない画面へ飛んで何も起きない。

- 一覧画面 → 行クリック / 「詳細」ボタンで `navigate("◯◯詳細")`
- 詳細画面 → `「← ◯◯に戻る」` で `navigate("◯◯")`
- それ以外の操作（新規作成・編集・削除など）は、遷移させずモーダル(`dialog`)や
  インライン表示で画面内に完結させる

## テーマ

`artifacts/brand.json` の `palette.primary` があれば `mvp-theme` が daisyUI 5 の
完全テーマ（20 色 + radius + depth）を設計する。無ければ `assemble.ts` が
`paletteToTheme()` でブランドパレットから機械的に導出する（エージェント不要）。

`theme.json` がスキーマに合わなければ、`assemble.ts` は警告を出してパレット導出に落とす。
プロトタイプが真っ白になることはない。

## 部分再生成（非破壊）

```bash
pnpm exec tsx .claude/skills/mvp-pipeline/scripts/plan-screens.ts <projectDir> "顧客" "スタッフ"
```

指定した画面（＋その詳細画面、親を指定した場合は配下）だけプロンプトを作り直し、
それ以外は `prototype/screens/<i>.jsx` をそのまま再利用する。
テーマも既存のものを使い回す（配色の一貫性を保ち、生成時間を節約する）。

**未生成の画面は指定に関わらず必ず作る**ので、失敗画面の作り直しは安全に繰り返せる。

画面ソースは `screens/<番号>.jsx` に番号で保存している。番号はナビ順から決まるので、
`navigation` を作り直すと同じ番号が別の画面を指し得る。`plan-screens.ts` は前回の
`plan.json` と突き合わせ、**前回も同じ番号が同じ画面だったときだけ再利用する**
（ずれていれば作り直す）。ナビを変えたあとに部分再生成しても、別画面の中身が
紛れ込むことはない。

## よくある失敗と直し方

| `assemble.ts` の報告 | 原因 | 直し方 |
| --- | --- | --- |
| 未生成 | エージェントが `screens/<i>.jsx` を書かなかった | その画面だけ再生成 |
| 壊れている | 関数の形になっていない／括弧が閉じていない（出力途中切れ） | その画面だけ再生成。画面を分割するほど大きい場合はナビを見直す |
| 画面は出るが遷移しない | `navigate()` に存在しない画面名を渡している | プロンプトの「# 遷移」に無い名前を使っている。再生成する |
| 色が効かない | `bg-white` / `bg-gray-100` など生のカラーを使っている | daisyUI のセマンティックカラー（`base-100` 等）で書き直させる |

ブラウザのコンソールにエラーが出ている場合は Babel 変換の失敗（JSX の構文エラー）。
`sanitizeScreen` の括弧バランス検査をすり抜けた壊れ方なので、その画面を再生成する。

## 本体（Web アプリ）との差

- 本体は Anthropic の prompt caching で `[system + daisyUI リファレンス + アプリ文脈]` を
  キャッシュし、並列 N 画面で使い回す。Claude Code のサブエージェントはセッションが別なので
  **このキャッシュは効かない**（そのぶん実行コストは高い）。
- 本体は画面生成に高速モデル（haiku）を既定で使うが、Claude Code 版は `sonnet` 固定。
- 本体は生成物を DB（`prototypes` テーブル）に保存する。Claude Code 版はファイルのみ。
  Web 側 DB が正なので、`.mvp/` はコミットしない。
